# Docker 应用部署与管理

面向个人开发者和中小型公司自建实例中的可信成员。当前功能以“仓库镜像地址 + 单个 HTTP 服务”为范围，不在服务器构建用户源码；功能取舍遵循 [产品定位与原则](REQUIREMENTS.md#1-目标)。

## 部署权限与服务边界

增加独立的 `runner` 容器，用平台 Go 二进制提供受限接口：

- 运行器使用 root 用户，持久挂载 `/var/run/docker.sock`。该 socket 实际拥有控制宿主 Docker 的高权限；限制 API 参数不能消除运行器本身被入侵的风险。
- 后台 API 不挂载 Docker socket，仅以 UID 10001 访问私有 Unix socket `/run/stacknest-runner/control.sock`。
- 运行器不监听 TCP。控制目录和 socket 限制到平台用户，用户应用不挂载它们。
- 运行器仅操作带有本实例及应用编号标签的容器、网络；不能经公开应用接口指定任意容器编号或主机目录。
- 运行器读取 Docker 存储文件系统的剩余空间；将 Docker 存储根目录只读挂载为 `/docker-storage`。
- 运行器本身限制为 96 MiB、0.5 CPU、64 PID，根文件系统只读，仅开放管理数据目录所需 capabilities。启用 XFS 数据配额时只向受信任 Runner 增加 SYS_ADMIN，用户应用不获得该权限。

## 用户应用约束

- 普通用户仅管理自己的应用，管理员管理全部。删除普通用户时应用转交管理员。
- 默认最多 3 个应用，内存分配总额 768 MiB（停止的应用仍占配额）。超管可在 Docker 应用页的“资源配置”调整实例预算；单个应用限制为 64–1024 MiB、0.1–1 CPU、128 PID，无额外 swap。
- 每个应用使用独立 Docker bridge，宿主不发布应用端口；Go 通过运行器代理 HTTP、流式响应、WebSocket。
- 未启用联网配置时保持 internal 网络；启用 [局域网保护](NETWORK_EGRESS.md) 后允许公网和 Linux 宿主服务访问，阻止直接访问其他局域网设备。不提供多容器 Compose 或项目数据库编排。
- 固定非特权配置，无 host network、Docker socket 或任意宿主 bind，禁止提权并移除部分 capabilities。
- 一个可选数据目录映射到平台数据卷中的 `apps/{应用UUID}/data`；更新、重启保留，永久删除应用时清理。
- 镜像解压后上限 1 GiB；拉取监控 Docker 磁盘，达到 90% 或无法预留空间则拒绝 / 中止。空间预检不等于硬配额，真正的硬限额另需 XFS＋prjquota＋传统 overlay2 和 `compose.quota.yaml`，见 [磁盘配额](STORAGE_QUOTAS.md)。普通 ext4 部署没有这些硬限额。
- 每容器日志 5 MiB × 2，接口取最近 200 行、最多 256 KiB。配置变量值与仓库密码进一步遮盖。
- 环境变量、仓库密码使用与应用 ID 绑定的 AES-GCM 密文保存。迁移必须保留 `STACKNEST_AUTH_SECRET`。

适用受信任的个人开发者和中小型公司私有项目管理。共享内核的 Docker 容器不提供恶意租户的强隔离；已有权限与资源保护仍需保留，以应对误操作、应用漏洞和资源争抢。

联网作为可选宿主配置：Go 宿主服务维护独立 nftables 表，超管可通过网络设置页面修改网卡、网段及端口例外，Runner 只读其就绪状态；缺少保护时拒绝新的联网操作。规则仅作用于本产品的应用网桥，不切换 Docker 防火墙后端、不增加用户容器能力。安装与旧应用迁移见 [联网说明](NETWORK_EGRESS.md)。

### 配置密钥

`STACKNEST_AUTH_SECRET` 用于派生配置加密密钥，有应用后不能直接换值。当前不提供在线重加密；迁移保留原值。日志同时遮盖候选和生效配置中的已知值，不能识别应用自行产生的全部敏感内容。

## 更新与恢复

任务保存在 PostgreSQL，浏览器断开不影响执行。先拉镜像、创建候选容器，再停止旧容器启动候选。60 秒内等待就绪：默认检查端口；填写 HTTP 健康路径后，需要该路径返回 2xx。

部署失败时尽力恢复旧容器和配置，但**不恢复数据库结构或持久化数据**。新容器在启动阶段已经可能执行迁移或写入数据，旧程序也未必能读取变更后的数据。因此没有通用的“一键业务回退”，本版也不新增成功版本回退。破坏性数据库变更需由应用自行安排备份、兼容性检查和恢复。

应用域名为 `stack-nest--app-{标识}.项目基础域名`，SSH 隧道为 `stack-nest--app-{标识}.localhost:18080`，双连字符避免与现有静态项目的标识冲突。

## 健康检查与当前用量

- 表单可选填 `/health`、`/health/` 等绝对路径，不接受完整 URL、查询参数、片段或转义路径。探测只访问已确认应用的私有 IP 和容器端口，不走环境代理、不跟随重定向；每次 HTTP 请求最多两秒。
- HTTP 检查接受 200–299，3xx、4xx、5xx 和超时均失败。留空兼容旧应用的 TCP 检查，页面明确标注“端口可连接”，不把它等同于业务健康。
- 页面区分“进程运行中”和“HTTP 正常 / 检查失败”，可见时刷新 CPU、内存与进程 / 线程数。CPU 100% 表示一个核心，内存采用 Docker CLI 的 Linux 口径扣除非活跃文件缓存。
- 停止的应用不采样；采样失败或首次 CPU 增量不足时显示未知，不伪装成零。普通用户只读取自己的应用，管理员可以读取全部；接口不暴露环境变量、宿主统计或 Docker 原始返回。
- 本版不读取镜像自带的 HEALTHCHECK 结果，不自动重启 HTTP 异常的应用，不记录历史指标，不引入 Prometheus / Grafana。
- 更新健康路径会部署新一代容器；健康状态按当前容器实际的路径标签判断，避免未完成更新时使用候选配置判断旧容器。

## 开发检查

应用队列表使用手写 PostgreSQL 事务，`atlas.hcl` 的 `migration.exclude` 防止 Ent 差异生成误删 `container_apps`。新增 SQL 后使用 `atlas migrate hash --dir file://migrations`。

本地可运行 Go 模拟与临时 PostgreSQL 集成测试、`pnpm typecheck`、`pnpm lint`、Playwright 桌面和手机回归。

## 使用

后台进入“Docker 应用”，填写可拉取的镜像地址及镜像实际监听的端口。镜像使用其原有 ENTRYPOINT / CMD，需要监听 0.0.0.0；仅监听 127.0.0.1 的服务不可达。第一版是单个 HTTP 容器，不在服务器编译源码，不接收镜像 tar，不提供 Compose 数据库编排。

需要保存上传文件、SQLite 等内容时填写镜像内的数据目录；该目录在更新、重启、迁移后保留。其余容器文件系统视作可丢弃内容，重建不保留。编辑时环境变量默认保持原值，不回显密文；更换同名镜像标签后点更新会重新拉取，日常启停使用已确认的镜像 ID。

应用站点内容公开，管理操作按所有者隔离。应用无法读取后台会话 Cookie，也不能向后台设置同名 Cookie 或父域 Cookie。本版没有访问码功能。

## 备份与迁移

每日备份先停止后台任务，再停止本实例正在运行的应用，打包数据库与 apps 数据目录，最后恢复原本运行的应用。停止的应用不会因备份被启动。备份期间应用短暂不可访问。

迁移包额外包含应用固定镜像及数据目录，保持原有配置密钥。新实例按数据库记录重建自己的容器、网络，不沿用旧容器 ID。导出 --freeze 会保持后台及应用停止，用于最终切换；取消冻结时先执行 runner 的 apps-thaw，再 start stacknest。

数据归档允许 apps/<UUID>/data 内的相对符号链接及指向先前文件的硬链接；绝对链接、逃逸目录的链接、设备文件、通过链接祖先写入的条目会拒绝迁移。私有仓库密码及环境变量包含在加密数据中，迁移包仍需私有保存。

迁移只保留已确认的固定应用镜像；迁移时尚未完成的部署任务会恢复重试，仍需对应镜像仓库可用。迁移后显式更新镜像也需要正确的仓库地址。

运行器要求 Linux amd64 Docker、至少 1600 MiB 宿主内存，使用 Docker API v1.45；此前在 ECS 的 Docker 29.4.3 验收，迁移后在新虚拟机 Docker 29.1.3 复验。数据硬配额另外要求 Linux 5.14+ 和 XFS 项目配额。

新服务器的本地演示镜像仓库另行迁移，只监听 `127.0.0.1:15000`，数据卷 `stacknest-smoke-registry-data`。显式更新拉取已核对；它是测试辅助服务，通用迁移工具不会自动迁移 Compose 之外的仓库。

## 实例资源预算与部署反馈

升级需应用 `20261011170000_app_limits.sql`，并同时更新后台、Runner 和前端。迁移保留原有默认值，不重建已有用户应用；配置存入 PostgreSQL 的单行 `app_limits` 表，随数据库备份和迁移一起保存。

超管在 Docker 应用页打开“资源配置”，调整实例最多应用数（1–100）和应用内存总预算。内存预算不得超过 Docker 宿主允许的上限：至少为系统与平台预留 832 MiB 和四分之一总内存，取较保守值。这个上限用于避免明显超额分配，不保证任意工作负载都不会耗尽系统资源。单个应用仍有自己的 CPU、内存及磁盘限制。部署表单默认分配 256 MiB，单应用最高 1024 MiB；当前家庭虚拟机的实例总预算已调整为 2048 MiB，最多应用数保持 3 个。全新安装仍从 768 MiB 的保守预算开始，由超管根据宿主容量调整。提高预算不会立即占用全部内存，也不会自动修改已有容器的额度。

停止或部署失败的应用仍预留名额和配置内存。新预算不得低于已有应用的预留值，有应用任务等待或执行时禁止保存；过期配置页面返回 409，需重新加载。保存与创建应用共用数据库事务锁。更新应用期间预留旧版和候选版中较大的内存，新版成功后才释放旧额度；失败恢复旧配置。修改实例预算不会改变已有容器的资源参数。

仅超管能读取实际全局预留量、宿主可配置上限或写入预算。普通用户及管理员可读取配置后的应用限制，不能读取其他用户的预留量。接口说明见 `openapi/app-limits.yaml`。

应用卡片显示当前任务阶段：排队、准备、拉取与校验镜像、创建和启动容器、健康检查、清理，失败更新可显示恢复旧容器和失败阶段。拉取镜像时显示 Docker 已报告镜像层的下载字节合计；缓存层、解压和健康检查没有整体百分比，新层发现时总量可能增加。

进度快照按应用编号及任务代次隔离，保存于 Runner 的有界内存，最长保留 30 分钟；刷新浏览器仍能读取，Runner 重启会丢失快照。任务及最终结果仍保存在数据库，中断后重新排队执行；进度快照不作为持久日志。公开响应不包含仓库事件原文或凭据。配置修改和新增邮箱记录受控操作日志。

## 应用详情、磁盘与日志

点击应用名称进入 `/apps/<id>`，状态与非敏感配置集中展示，`/apps/<id>/logs` 可以刷新、收藏和直接访问。普通用户仍只能查询自己的应用；UUID 路由不替代后端所有权校验。

磁盘分别显示容器可写层和持久化数据。启用 XFS 配额时读取内核实际分配块与硬上限，持久化数据同时展示 inode 用量；达到任意上限的 90% 提示清理。首次请求异步采样，最多每分钟一次，失败显示未知而非 0。停止状态也能采样；更新容器后不会复用旧容器计数。

未启用 XFS 数据配额时，可写层使用 Docker 逻辑文件大小估计并明确标注，持久化目录不递归扫描。两项均不包含镜像共享层、容器日志和 tmpfs；不能将其合计当作宿主磁盘总用量。

运行日志是最近 200 行、最多 256 KiB 的快照，自动刷新间隔 5 秒，只在可见页面串行读取。搜索仅过滤当前快照，向上滚动暂停跟随，勾选“跟随最新”可恢复。它不是完整日志归档；既有敏感值脱敏仍生效。

只读部署自检命令与解释见 [首次部署与自检](GETTING_STARTED.md)。
