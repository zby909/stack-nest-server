## 优先修复

### 1. P1：上传页面与管理后台共用来源

位置：`internal/httpserver/static.go:13`、`internal/httpserver/auth.go:100`、`web/vite.config.ts`；当前 SSH 入口的 `tunnel.conf` 也把 `/sites/` 代理到 Go。

本地与 SSH 入口能在管理地址下直接打开 `/sites/{slug}/`。普通用户可以上传含 JavaScript 的 HTML；管理员在已登录状态下打开这种页面时，页面与管理 API 同源，可以自动携带管理员 Cookie 发起请求。HttpOnly 防止脚本读取 Cookie，但不会阻止脚本使用浏览器现有会话。

复现：普通用户上传带无害脚本标记的 HTML；预览返回 200 且没有沙箱响应策略；按该页面中同源请求的语义构造 `POST /api/users`，携带管理员会话后返回 201。此为隔离 HTTP 测试，没有在真实浏览器或生产环境执行攻击脚本。服务器现有 `/sites/testhtml/` 也实测可经 SSH 入口访问。

建议：把上传站点放到与后台不同的浏览器来源，并确保管理入口不能再通过其他路径执行上传内容；本地和 SSH 模式也应遵守同样边界。正式公网使用独立项目子域名的方向是正确的，不应将本项描述为已经攻破公网的子域名隔离。[浏览器同源规则](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy)把协议、主机和端口作为来源，路径不同不会形成隔离。

### 2. P1：Git 忽略规则误排除了后端启动代码

位置：`server/.gitignore:7`。

未加路径限定的 `stacknest` 同时匹配 `cmd/stacknest/`。实测 `git check-ignore -v cmd/stacknest/main.go` 命中该规则，导致正常提交源码时缺少程序入口，之后按 Git 检出无法构建。

建议：只忽略根目录构建产物，例如 `/stacknest` 和 `/stacknest.exe`，并在建立版本基线时检查完整源码集合。当前前后端仓库均尚无首次提交，版本留档仍待完成；本次没有代为提交。

### 3. P2：上传中断会产生无法管理的站点

位置：`internal/project/service.go:78`、`:104`，`cmd/stacknest/main.go:45`。

上传先将文件移动到最终 `sites/{slug}`，再写数据库。若在两步之间退出，普通错误分支的清理来不及执行；重启只恢复删除事务，不恢复未完成上传。

故障注入已复现：重启恢复后，列表为空但站点文件仍存在；删除 API 找不到记录；重新上传同一 slug 返回冲突。生产 Nginx 直接读取文件目录，因此这类文件还可能继续对外提供。

建议：为发布过程增加可持久化的进行中状态和启动恢复，在写库成功前避免公开最终目录；同时处理遗留 `tmp/upload-*`、`.publish-*`。状态不明确时应保留或隔离现场，避免简单扫描后盲删。

### 4. P2：Cloudflare 后面的登录限流没有按真实访客区分

位置：`deploy/nginx/cloudflare.conf.template:41`、`internal/httpserver/auth.go:159`。

当前 Nginx 把 `$remote_addr` 写入 `X-Real-IP`，有效配置中没有真实 IP 还原。经 Cloudflare 访问时，后端因此按回源代理 IP 计数；不同访客可能共用额度，同一访客也可能经不同代理 IP 计数。代码中的“按客户端 IP 限流”与实际部署不一致。

建议：仅对可信 Cloudflare 来源还原访客 IP，再向 Go 传递；直连请求不能随意伪造受信请求头。配置方式参见 [Cloudflare 原始访客 IP](https://developers.cloudflare.com/support/troubleshooting/restoring-visitor-ips/restoring-original-visitor-ips/) 和 [Nginx realip 模块](https://nginx.org/en/docs/http/ngx_http_realip_module.html)。本次已核对服务器生效配置，但没有在受备案影响的公网链路上实测多访客限流。

### 5. P2：上传大小应与公网入口限制一致

位置：`internal/config/config.go:39`、`web/src/App.tsx:85`、`web/src/api/projects.ts`。

前后端允许文件本身达到 `100 * 1024 * 1024` 字节，还需要 multipart 表单开销。[Cloudflare Free 的请求上传上限为 100 MB](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/4xx-client-error/error-413/)，站点还可另设更低限制。靠近当前上限的文件可能通过前端校验，却在边缘被 413 拒绝。

建议：按实际入口上限制定统一文件限制并预留请求开销，例如第一版先用 90 MiB；同时正确展示边缘返回的 413。此项来自代码与官方限制的对照，未进行公网大文件上传。

## 数据与部署需要补齐

- **自动备份和恢复演练。** 服务器目前可见的是三个发布前备份目录；检查 root crontab、systemd timers 和常规系统任务目录，未发现 StackNest 自动备份任务。已有文档中的数据库与文件成套备份思路合理，应补固定执行、失败记录、保留期限、服务器外副本，并实际恢复一次。仅有备份文件不能证明可恢复。
- **统一缓存策略。** 项目 Nginx 路由没有明确缓存响应头，也没有删除时清理 CDN 的流程。Cloudflare 默认会缓存 JS、CSS、图片等资源；删除或复用同一域名后，已缓存资源可能仍然返回。第一版可先采用要求重新验证或不缓存的明确策略，再考虑版本化资源与自动清理。此为基于配置和 [Cloudflare 默认缓存规则](https://developers.cloudflare.com/cache/concepts/default-cache-behavior/) 的风险判断，尚未在公网复现。
- **发布流程可重复。** 通用 Compose 文档与当前离线构建、SSH 辅助入口的实际流程需有明确对应。可复用的部署脚本应进入源码管理，机器配置、证书、授权码、备份继续保存在私有目录。
- **验收状态有依据。** 更新需求文档时记录环境、日期和证据；本次数据库测试通过不能代替真实邮箱、浏览器、公网域名和恢复验收。
